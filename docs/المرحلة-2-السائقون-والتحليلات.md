## 1) ما تم بناءه

### أ) صفحة "السائقون" (جديدة)
- **بطاقات ملخص أعلى الصفحة:** إجمالي السائقين بالشركة، السائقون النشطون، أقل فرع تغطية (أقل عدد سائقين نشطين).
- **جداول مجمّعة حسب الفرع** (`branch_id`/`branch_name` من صف المستخدم):
  - لكل فرع: عدد النشطين + العدد الإجمالي في الرأس.
  - لكل سائق: الاسم، البريد، الهاتف، حالة الحساب (نشط/معلّق/قيد المراجعة/مرفوض)، **عدد الطلبات المكتملة**.
  - السائقون بلا فرع يُجمَّعون تحت "بدون فرع".
- رابط "السائقون" في القائمة الجانبية (أيقونة `Truck`) + مسار `/director/drivers`.

### ب) صفحة "تحليلات الأصناف" (جديدة)
- **فلتر فترة زمنية** (آخر 7/30/90 يوم — افتراضي 30) يعيد حساب القسمين.
- **قسم "الأكثر طلباً 🔝":** أعلى 10 أصناف بكمياتها الإجمالية وعدد الطلبات، مع شريط نسبي (bar) مبسّط.
- **قسم "الأصناف الراكدة ⚠️":** الأصناف المتوفرة بالمخزون (كمية > 0 في أي فرع) ولم تُطلب خلال الفترة، مع مجموع الكميات المتوفرة + تاريخ آخر طلب أو "لم يُطلب مطلقاً".
- رابط "تحليلات الأصناف" في القائمة الجانبية (أيقونة `BarChart3`) + مسار `/director/item-analytics`.

## 3) البنية الفعلية المعتمدة (مصدرها migrations 0001-0008 في مشروع Flutter الأصلي، وتم التحقق من تطابقها مع قاعدة البيانات الحية عبر PostgREST)

قبل كتابة أي استعلام، روجعت ملفات:
`stitch_medlink_yemen/supabase/migrations/0001_initial_schema.sql` و `0002_catalog_inventory_orders.sql` و `0003...0008`، وثُبّتت أسماء الأعمدة هذه ضد قاعدة البيانات الحية (استعلامات REST ناجحة):

| الجدول | الأعمدة المستخدمة |
|---|---|

## 4) القرارات التقنية

1. **قراءة فقط (no writes)** — كل الاستعلامات تمر عبر supabase-js بالصلاحيات الموجودة: سياسات RLS في migrations تسمح للمدير العام بقراءة `users`/`orders`/`order_items`/`products`/`inventory`. **لا حاجة لأي Edge Function جديدة** ولا لنشر أي دالة.
2. **عدّ الطلبات المكتملة لكل سائق:** استعلام واحد على `orders` حيث `status='delivered'` و `assigned_driver_id` غير فارغ، ثم عدّ client-side — بدل N+1 queries.
3. **الأكثر طلباً — الاستعلام الدقيق (PostgREST):**
   ```
   /rest/v1/order_items?select=product_id,quantity,order_id,orders!inner(status,created_at)
        &orders.created_at=gte.<now - N يوم>&orders.status=neq.cancelled
   ```
   ثم تجميع: Σ `quantity` لكل صنف + عدد الطلبات الفريدة (unique `order_id`)، ترتيب تنازلي وأخذ أعلى 10. `!inner` يجعل join داخلياً على الفترة؛ واستُبعدت `cancelled` حتى لا تُحتسب طلبات ملغاة كطلب فعلي.
4. **الأصناف الراكدة:** (1) أجمع `inventory.quantity > 0` لكل صنف (المرشحون)، (2) أستعلم `order_items` خلال الفترة لنفس الأصناف وأستبعد المطلوبين منها، (3) للباقي: آخر `created_at` عبر كل الفترات — إن لم يوجد أي سطر قط → "لم يُطلب مطلقاً".
5. **ترشيح التجميع في الواجهة بدلاً من SQL RPCs:** الكميات متوسطة، وRPC إضافي كان سيتطلب نشراً — اختُصرت الدورة بـ client-side aggregation فقط، مع تكسير استعلامات `in()` لدفعات من 100.
6. **التسميات العربية في الجداول** بطريقة مطابقة لبقية شاشات المدير العام (ألوان `emerald/amber/blue` وظلال شفافة).

## 5) تعديلات قاعدة البيانات

**لا يوجد أي تعديل (migration جديد) مطلوب ولا أي ملف SQL أُنشئ أو عُدّل في هذه المرحلة.** التحليلات مدعومة بالكامل بالبنية القائمة (`order_items.quantity` + `orders.created_at` + `inventory.quantity`):

| المتطلب | العمود الموجود القائم على مخطط 0002 |
|---|---|
| مجموع الكميات المطلوبة لكل صنف | `order_items.quantity` |
| تصفية الفترة الزمنية | `orders.created_at` / `order_items.created_at` |
| "متوفر بأي فرع" | `inventory.quantity > 0` |
| عدد الطلبات لكل صنف | `COUNT(DISTINCT order_items.order_id)` |
| "لم يُطلب مطلقاً" | غياب سجلات `order_items` للصنف |
| الطلبات المكتملة لكل سائق | `orders.status='delivered' AND orders.assigned_driver_id = <السائق>` |
